## 2. User groups

| Group | Questions they ask daily | BRs |
|---|---|---|
| Executives | How is revenue tracking against the last hour? Which category is driving it? | BR1 |
| Growth & Marketing | Where do customers drop out of the funnel? Which segment deserves ad spend? Who abandoned a cart? | BR2, BR4, BR5 |
| Merchandising | Which products are rising? What sells alongside product A? | BR3, BR7, BR9 |
| Operations & Risk | Which SKUs are about to run out? Which accounts order abnormally? | BR6, BR8 |

## 3. Source data

Event log — REES46 "eCommerce behavior data from multi category store" (Kaggle).
Use the `2019-Nov.csv` file, 67,501,979 rows covering 1-30 November, and sample it
down to ~4.7M by taking **~7% of `user_id` values across the whole month** — never the
first 5M rows. The first 5M rows are about two days of November, which leaves BR4's
recency meaningless and BR6's `velocity_7d` with fewer than seven days to average over.

November is the larger of the two REES46 months (October has ~42M rows); the 7% keeps
the sample under the 5-million-row cap.

```

event_type      string      view | cart | remove_from_cart | purchase
product_id      bigint      44600062
category_id     bigint      2103807459595387724
category_code   string      electronics.smartphone      (nullable)
brand           string      samsung                     (nullable)
price           decimal     489.07
user_id         bigint      541312140
user_session    string      9333dfbd-b87a-4708-9857-6336556a0fcc
```

Inventory table — generated by script, documented as synthetic in the report:

## 4. Three data tiers

| Tier | Contents | Layout |
|---|---|---|
| Bronze | Raw events, untouched. The reference copy when a number looks wrong | Parquet, partitioned by `event_date` |
| Silver | Cleaned: drop `price <= 0`, drop null `user_id`, split `category_code` into `category_l1/l2/l3`, fill missing `brand` with "unknown", normalise timestamps to UTC+7 | Parquet, partitioned by `event_date` then `event_type` |
| Gold | Pre-aggregated tables, one per BR. This is what the application actually reads | Cassandra (real-time) or Parquet (analytical) |

Silver is partitioned by `event_type` because most queries care about one event type
only, so Spark skips whole directories without opening a file. That is *partition
pruning*, one of the techniques covered in the presentation.

## 5. Cassandra schema

Cassandra cannot filter arbitrarily, so keys are designed backwards from the
question each screen will ask.

```sql
-- BR1: GMV per minute, for the executive screen
CREATE TABLE gmv_by_minute (
  event_date    date,
  category_l1   text,
  window_start  timestamp,
  gmv           decimal,
  order_count   int,
  PRIMARY KEY ((event_date, category_l1), window_start)
) WITH CLUSTERING ORDER BY (window_start DESC);

-- BR3: trending products, 15-minute sliding window
CREATE TABLE trending_products (
  window_start  timestamp,
  rank          int,
  product_id    bigint,
  brand         text,
  category_l1   text,
  view_count    int,
  cart_count    int,
  PRIMARY KEY (window_start, rank)
);

-- BR5: abandoned carts, for the CRM team
CREATE TABLE abandoned_carts (
  event_date    date,
  cart_value    decimal,
  user_session  text,
  user_id       bigint,
  item_count    int,
  last_event_at timestamp,
  PRIMARY KEY ((event_date), cart_value, user_session)
) WITH CLUSTERING ORDER BY (cart_value DESC);

-- BR6: stock-out risk per warehouse
CREATE TABLE stockout_risk (
  warehouse_id      int,
  days_to_stockout  float,
  product_id        bigint,
  stock_on_hand     int,
  velocity_7d       float,
  PRIMARY KEY ((warehouse_id), days_to_stockout, product_id)
);

-- BR8: order velocity alerts
CREATE TABLE order_velocity_alerts (
  event_date    date,
  window_start  timestamp,
  user_id       bigint,
  order_count   int,
  total_value   decimal,
  severity      text,
  PRIMARY KEY ((event_date), window_start, user_id)
) WITH CLUSTERING ORDER BY (window_start DESC, user_id ASC);
```

Reasoning behind the keys, to be reused in the report:

- BR1: the partition key is `(event_date, category_l1)` because the screen always
  filters by date and category. Clustering by `window_start DESC` means "the last
  60 minutes" reads exactly 60 adjacent rows at the head of one partition, with no
  sort step.
- BR5: clustering by `cart_value DESC` means "the 50 highest-value carts today"
  comes back without sorting, because the rows are already in that order on disk.
- BR6: `days_to_stockout` ascending puts the most urgent SKUs at the head of the
  partition.

Both `stockout_risk` and `abandoned_carts` cluster on a value that *changes between
runs* — days remaining, cart value. An upsert therefore writes a new row instead of
replacing the old one, and the screen shows the same product or cart twice with two
different numbers. Every batch rewrite must `DELETE` the partition first
(`DELETE FROM stockout_risk WHERE warehouse_id = ?`) and then insert. This costs one
extra statement per partition and is the only correct option without a second table.

## 7. Life of an event

1. `replayer.py` reads the bronze CSV, sorts by `event_time`, and every 5 seconds
   writes a JSON file of roughly 2,000 rows into `data/stream_landing/`. A speed
   factor compresses playback so a demo does not have to wait: one hour of real
   data can replay in one minute.
2. `streaming_gold.py` is already running with
   `readStream.format("json").schema(EVENT_SCHEMA).load("data/stream_landing/")`.
   Spark picks up the new file in its next micro-batch.
3. Inside the micro-batch: clean the rows, split `category_code` into three levels,
   and apply `withWatermark("event_time", "10 minutes")` so old state can be dropped.
4. Four aggregations run over that same stream: GMV in 1-minute windows (BR1);
   top-N over a 15-minute window sliding every minute (BR3 — Structured Streaming
   cannot rank a streaming DataFrame, so the ordering and the top-N cut happen inside
   `foreachBatch`, where the micro-batch is an ordinary static DataFrame); sessions with a `cart`
   and no `purchase` after 30 minutes (BR5); orders per user in 5-minute windows
   with a severity label (BR8).
5. Each aggregation ends in `foreachBatch`, where plain `cassandra-driver` code
   upserts the result. Checkpoints go to `data/checkpoints/<job_name>/`.
6. `batch_silver.py` builds `data/silver/` from bronze using the cleaning rules in
   section 4. This is what creates silver in the first place, and it runs before any
   batch job — including in week 39, before the streaming job exists. In parallel, once
   the stream is running, it appends its own cleaned rows to the same directory. Silver
   has two writers by design; the batch one is the one the schedule depends on.
7. `batch_gold.py` runs on a schedule, or by hand during a demo: it reads silver
   and computes the funnel, RFM, affinity and stock-out risk, writing to Parquet
   gold and to Cassandra.
8. FastAPI routes each request: BR1/3/5/6/8 hit Cassandra with a point query on the
   partition key; BR2/4/7/9 let DuckDB read the gold Parquet directly.
9. React renders. Target: every screen responds in under 2 seconds.

## 8. The eight screens

| Screen | BR | Reads from | Components | Filters |
|---|---|---|---|---|
| Real-time executive | BR1 | Cassandra | Four large metric cards plus a GMV line chart for the last 60 minutes, refreshing every 10s | Date, category |
| Conversion funnel | BR2 | Parquet | Three-stage funnel chart plus a conversion rate table by category | Date range, category |
| Trending products | BR3 | Cassandra | Top 20 table with rank-change arrows against the previous window | Time window |
| Customer segments | BR4 | Parquet | 5x5 RFM heatmap plus a customer list for the selected cell | Snapshot date, segment |
| Abandoned carts | BR5 | Cassandra | List sorted by cart value descending, plus a simulated "create campaign" action | Date, value threshold |
| Inventory alerts | BR6 | Cassandra | SKU table coloured by days remaining, red under 3 days | Warehouse, day threshold |
| Bought together | BR7 | Parquet | Product search box, then 10 related products with their lift scores | Anchor product |
| Risk alerts | BR8 | Cassandra | Alert timeline by severity, expandable to the underlying orders | Date, severity |
| Ad-hoc lookup (bonus) | BR9 | Parquet | Combined filters, with query time shown on screen | Category, brand, price, date |

## 10. Running the system

```bash
# 1. Infrastructure
docker compose up -d                 # Cassandra + Postgres
python serving/apply_schema.py       # Create keyspace and tables

# 2. Load base data (once, 5-10 minutes)
python ingestion/load_bronze.py --rows 5000000   # samples users across the month
python processing/batch_silver.py                # bronze -> silver. Batch needs this
python ingestion/gen_inventory.py

# 3. Real-time stream (two terminals)
python processing/streaming_gold.py       # start FIRST, let it wait
python ingestion/replayer.py --speed 60   # 1 hour of data per minute

# 4. Batch (any time after silver has data)
python processing/batch_gold.py

# 5. Application
uvicorn serving.api.main:app --reload
cd web && npm run dev
```

The order in step 3 matters: the streaming job must be running before the replayer
starts.

## 11. Comparison tier

Postgres and DuckDB do not serve the application. They exist to satisfy the course
requirement to "introduce at least one alternative solution for comparison".

| | PostgreSQL | DuckDB |
|---|---|---|
| Data | The same 5M silver rows, loaded into one table. Loading Postgres from the raw CSV instead would compare two different datasets and void both the benchmark and the correctness check | Reads the Parquet files directly, no load step |
| Purpose | Compares a traditional single node against the distributed design. Produces `EXPLAIN ANALYZE` output, the best illustrative material for the presentation | Computes ground truth for the correctness criterion, and doubles as the second alternative solution for bonus marks |
| Indexing techniques shown | B-tree, BRIN, partial, composite | Zone maps, vectorised scan over Parquet |

The benchmark query set lives in `benchmark/queries.sql` and runs identically
against every configuration. That is what makes the numbers comparable.

## 12. What this system deliberately does not do

Stating the limits in the report makes the conclusion stronger than pretending
everything is production grade, and it defuses the hard questions during defence.

- No real cluster. Spark runs locally, Cassandra is a single node. Performance
  conclusions are relative between configurations, not production figures.
- The real-time feed is a replay, not a live stream. Event ordering is cleaner than
  reality and there is almost no late-arriving data.
- The inventory table is synthetic, so BR6 proves the mechanism but does not
  reflect real warehouse behaviour.
- No authentication or authorisation. The dashboard assumes an internal network.
