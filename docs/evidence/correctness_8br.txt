== The independent answer ==
checks/correctness_8br.py: plain DuckDB SQL over data/silver/ (BR6: data/inventory/), written from
BR_SCOPE and API_CONTRACT, importing nothing from processing/. Each BR's rule in one line:
  BR1  per minute and top category plus an 'all' row: sum(price) and count of purchases
  BR2  per session: furthest step reached (view 1, cart 2, purchase 3), overall and per category;
       counted by the session's start date, with the raw event counts
  BR3  15-minute windows sliding every minute, closed by the watermark: top 20 by views, then
       carts, then product_id
  BR4  RFM at 30 Nov: ntile(5) over buyers for recency (descending), frequency, monetary, ties
       broken by user_id; the six segment rules; no purchase gives no_purchase
  BR5  a session split at a 30-minute gap; a split with a cart and no purchase, closed by the
       watermark; keyed by the date of its last event, the latest split kept
  BR6  units sold per day rebuilt from the balance itself (stock today = stock yesterday +
       received - sold), velocity = units of 24-30 Nov / 7, days = stock / velocity, 9999.0 at 0
  BR7  distinct (session, product) purchases; products in >= 20 sessions; pairs seen >= 3 times;
       support and lift, kept when lift > 1, both directions
  BR8  purchases per user in 5-minute tumbling windows; low 1-2, medium 3-9, high >= 10

A row matches when its key and every compared value are equal: money to the cent, floats within
1e-4 relative (Cassandra float is 32-bit). Score = matched / max(answer rows, stored rows), so a
missing row and an extra row both count. Threshold 99%.

== BR4's raw values ==
rfm_segments projects the current dim_user row, and a dim_user version keeps the values of the
snapshot that opened it: a version changes only when rfm_cell changes. So the scores and segment
(what the heatmap counts and filters on) match the 30 Nov answer for every user, while the raw
values in the cell list can be from an earlier snapshot. DuckDB, rfm_segments against
stg_rfm_snapshot at 30 Nov: recency_days differs for 23,198 users, frequency or monetary for 590,
any of the three for 23,353 (= 258,330 - 234,977). The same 23,198 and 590 as Session 17. Kept as
designed (Khang's answer on #17, 18 Oct); a limitation for report section 6.
